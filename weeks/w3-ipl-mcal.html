같은 LED, 세 가지 높이에서 켜기

2주차에는 주소 0x4029131E에 직접 1을 썼어요. 이번에는 NXP 드라이버(IPL)와 AUTOSAR 표준 드라이버(MCAL)로 똑같은 D13 LED(PTA29)를 켜 보고, 층이 올라갈수록 무엇이 숨겨지는지 비교해요.

01왜 다시 GPIO인가: 추상화

2주차 방식은 프로젝트가 커지면 핀 번호, 베이스 주소, 오프셋 계산이 여러 파일에 흩어져요. 보드가 바뀌면 그걸 전부 찾아서 고쳐야 해요.

추상화의 진짜 뜻 (서술형)하드웨어를 숨기거나 모르게 만드는 게 아니에요. 하드웨어 의존성을 코드의 어디에 모아 둘지 정하는 설계 방법이에요.

얻는 것 네 가지: ① 이식성(MCU가 바뀌어도 응용 코드는 그대로) ② 표준화(같은 API 규격) ③ 분업(설정 담당과 로직 담당을 나눔) ④ 안전성(검증된 드라이버를 재사용해 결함이 줄어듦)

03왜 13U인가: 포트를 반으로 나누는 IPL

    
SIUL2는 32비트 GPIO 포트를 16비트씩 반(Half)으로 나눠 관리해요. PTA[15:0]은 Low Half, PTA[31:16]은 High Half(PTA_H_HALF)예요. 그래서 IPL에는 "몇 번째 Half의 몇 번째 핀"으로 알려 줘야 해요. 끌어서 바꿔 보세요: PTA29

    

      

      

      

    

    
낚시 1Siul2_Dio_Ip_WritePin()에 핀 번호 29U를 그대로 넣으면 감점이에요. PTA_H_HALF와 상대 번호 13U(29 − 16)를 같이 줘야 해요. MCAL의 Dio 설정도 같은 이유로 Dio Port Id = 1(PTA[31:16]), Channel Id = 13이에요.

05Port 모듈 vs Dio 모듈: 누구 담당?

    
MCAL에서 핀 일은 두 모듈이 나눠 가져요. Port는 시작할 때 한 번 핀이 "어떤 핀인지"를 정하고, Dio는 실행 중에 이미 정해진 핀의 값을 읽고 써요. 아래 일을 하나씩 눌러서 담당을 맞혀 보세요.

    

      

      

        
PortPort_Init(NULL_PTR) · 시작 시 1회 · Port_Cfg.h, Port_PBcfg.c

        
DioDio_WriteChannel(), Dio_FlipChannel() · 런타임 · Dio_Cfg.h

      

      

    

    
낚시 2"핀 방향(Output)과 Mux를 설정하는 함수는 Dio_Init()이다?" 오답이에요. 방향과 Mux는 Port(Port_Init)가 맡고, Dio는 High/Low 입출력만 해요.

07빌드 크기(.text)만 보고 판단하면 안 되는 이유

    
빌드하면 콘솔에 text | data | bss | dec | hex | filename이 나와요. text는 Flash에 들어가는 코드와 읽기 전용 데이터, data는 초기값이 있는 전역 변수, bss는 0으로 초기화될 전역 변수예요. 실제로 재 보면 MCAL 쪽 .text가 IPL보다 커요.

08설정할 때 빠지기 쉬운 함정

    
낚시 3MCAL 프로젝트에서 Peripherals에 Port와 Dio를 추가할 때, Drivers 밑에 있던 Siul2_Port를 꼭 지워야 충돌이 안 나요.

    
Dio_FlipChannel 링크 에러(void)Dio_FlipChannel(LED_CHANNEL);은 현재 값을 읽어서 반대로 바꿔 줘요. 그런데 Peripherals › Dio에서 DioFlipChannelApi를 true(STD_ON)로 켜고 [Update Code]를 하지 않으면 미정의 심볼 링크 에러가 나요. 실습에서 Dio_WriteChannel을 쓰는 건 LOW/HIGH가 코드에 그대로 보여서 배우고 디버깅하기 쉬워서예요.
